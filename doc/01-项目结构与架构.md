# 项目结构与架构

## 1. 总体分层

当前工作区不是单一 App，而是三层：

```
ESP32S3/
├── README.md / demo/ / doc/          根骨架
├── MotoNav_stopwatch/                上游参考快照（被 .gitignore 忽略）
│   ├── firmware/boards/175/          1.75 通用固件（1.75C 实际使用）
│   ├── firmware/boards/185b/         1.85B 实验固件
│   ├── firmware/boards/stopwatch/    M5Stack StopWatch 专用固件
│   ├── firmware/libraries/           共享 Arduino 库
│   ├── android/standard/             标准版 App
│   ├── android/countdown/            读秒版组件（合并进高德车机版）
│   ├── ios/                          iOS App
│   └── docs/ scripts/ tools/         上游文档和工具
└── ports/175c/                       1.75C 固件移植层
    ├── pin_config.h
    ├── build.py / build.sh / build.ps1
    ├── dist/
    ├── diag/battery_probe/
    └── README.md
```

- **上游快照**：来自 `Charlie-healer/MotoNav_stopwatch` 的 `feat/board-m5stopwatch` 分支，提交 `b3c9929`，没有 `.git`，是只读参考。
- **1.75C 移植层**：不改上游固件，只在构建时复制 `boards/175` 并覆盖 `pin_config.h`。
- **Android 产品线**：标准版是独立 App；读秒版最终是高德车机版修改包，两者包名和构建链路不同。

## 2. 固件（系统）架构

### 2.1 板级抽象

每个板型一个目录：

```
firmware/boards/{175,185b,stopwatch}/MotoNav/
├── MotoNav.ino      程序入口和调度
├── pin_config.h     板级引脚
└── ...              板型特有模块
```

板级差异集中在 `pin_config.h`。`MotoNav.ino` 按固定依赖顺序 `#include` 所有模块头文件，形成一个大的编译单元；模块之间共享全局状态，不是传统的多文件独立编译。

### 2.2 1.75 固件模块

`boards/175/MotoNav/src` 已模块化：

| 模块 | 职责 | 代表文件 |
|---|---|---|
| `core` | 板级对象、版本、依赖、共享状态 | `DeviceContext.h`、`FirmwareConfig.h` |
| `connectivity` | BLE 服务、配对、安全、HID 媒体键 | `Bluetooth.h`、`Notifications.h` |
| `protocol` | 文字命令、二进制分包、文字位图 | `CommandReceiver.h`、`BulkReceiver.h` |
| `display` | 双缓冲、旋转、QSPI 推屏 | `DisplayPipeline.h`、`RowWorker.h` |
| `map` | 栅格/矢量地图、路线、HUD、雷达特效 | `RasterRenderer.h`、`VectorMapReceiver.h` |
| `graphics` | 矢量绘制、进度环、车道、状态组件 | `VectorDrawing.h`、`ProgressRings.h` |
| `pages` | 首页、导航、天气、来电、配对、到达 | `HomePage.h`、`NavigationPage.h` |
| `power` | AXP2101 电量、轮询、关机 | `Battery.h`、`Shutdown.h` |
| `diagnostics` | 渲染性能基准 | `RenderBenchmarks.h` |

数据流：

```
BLE 命令 / 地图包
  → protocol 解析
  → 导航、地图、天气状态
  → pages 选择页面
  → graphics/map 绘制到内存画布
  → display 双缓冲 + QSPI
  → CO5300 AMOLED
```

### 2.3 StopWatch 固件

`boards/stopwatch` 是另一套 45 个文件的板级实现，包含：

- `AvatarEngine` / `CompanionMode`：伴侣模式和动态表情；
- `LeanAngleMeter` / `PageLeanMeter`：倾角、G 值；
- `SettingsPage` / `UiModern`：圆屏设置页和毛玻璃 UI；
- `PowerManager` / M5PM1：M5Stack 私有电源管理；
- `RtcRX8130`：StopWatch 的 RTC；
- `BoardStopWatchInit`、`WaitingScreen`、`DestHistory`、`MapThemes` 等。

这些模块**不在 1.75/1.75C 固件中**，也没有编译进当前 1.75C 镜像。

### 2.4 1.75C 移植层

`ports/175c` 的工作方式：

1. 复制 `MotoNav_stopwatch/firmware/boards/175/MotoNav` 到 `.build/MotoNav`；
2. 用 `ports/175c/pin_config.h` 覆盖引脚；
3. 用 arduino-cli 编译，FQBN 为 ESP32-S3、32 MB Flash、DIO、OPI PSRAM、`app3M_fat9M_16MB` 分区；
4. 打包 app 镜像和完整镜像。

上游 `MotoNav_stopwatch/firmware` 不被修改。

## 3. Android App 架构

### 3.1 标准版 `com.friday.motonav`

67 个源文件，板级无关，主要分四类：

- **页面**：首页搜索、圆屏显示、导航语音、圆屏设置、地图 Key；
- **后台/服务**：`NavService`、`BleLink`、`CallWatcher`、`MusicBridge`；
- **地图**：`MapFeeder`、`AmapSdkRaster`、`MapGeo`、`MapStylePolicy`；
- **天气/Key**：`Weather`、`QWeatherClient`、`Keys`。

手机负责 GPS、高德算路、地图抓取/栅格化、和风天气、音乐控制，通过 BLE 把数据和命令发给圆屏。

### 3.2 App 里的 StopWatch 痕迹

App 是 StopWatch 分支的共享 App，但 StopWatch 专属代码很少：

- `MainActivity.kt` 只有一处明确的 StopWatch 注释（开机动画精简）；
- `CallWatcher.onScreenTouch` 保留了 `DEST_Q`、`DEST_GO`、`SET_THEME` 分支；
- `syncDestinations()` 会发送 `#DEST` 命令。

这些是 StopWatch 固件的目的地抽屉和主题切换协议。**1.75 固件从不发送这些事件，也不处理 `#DEST`**，所以在 1.75C 上这些分支处于休眠状态。

### 3.3 读秒版

`android/countdown` 是 108 个文件的独立组件，最终合并进高德车机版：

- 内部组件包：`com.friday.motonav.countdown`；
- 最终安装包：`com.autonavi.amapauto`；
- 依赖 `provider.apk`、Zig 原生路径库、apktool 合并；
- 完整构建只支持 Windows。

### 3.4 iOS

`ios/` 是独立 Swift App，使用同一套 BLE 协议，不参与 Android 构建。

## 4. App ↔ 固件协议

| 方向 | 内容 | 1.75/1.75C | StopWatch |
|---|---|---|---|
| App → 圆屏 | 导航、地图、天气、音乐、来电 | 支持 | 支持 |
| 圆屏 → App | `T,W` 天气请求 | 支持（App 已补回处理） | 支持 |
| 圆屏 → App | `T,A` 接听 | 支持 | 支持 |
| 圆屏 → App | `DEST_Q` / `DEST_GO` | 不支持 | 支持 |
| 圆屏 → App | `SET_THEME` | 不支持 | 支持 |
| 圆屏 → App | `#DEST` 目的地列表 | 不支持 | 支持 |

这就是“App 和系统都有 StopWatch”的实际边界：

- **固件侧**：StopWatch 是一整套板级实现，只在 `boards/stopwatch` 编译；
- **App 侧**：StopWatch 分支的共享 App，只保留了少量 UI/协议分支；
- **1.75C 运行时**：固件是 175，App 是共享版；StopWatch 固件不参与，StopWatch App 分支休眠。

天气问题就是这个不对称造成的：StopWatch 分支为了自己的设置页，把 App 的天气触发和配置入口删了；1.75C 固件仍然有天气页，于是圆屏一直 loading。现已补回。

## 5. 构建与产物

| 对象 | 构建方式 | 产物 |
|---|---|---|
| 1.75C 固件 | `ports/175c/build.py` | `app_0x10000.bin`、`full_0x0.bin` |
| 标准版 App | Gradle 8.11.1 + JDK 17 | debug APK、release APK |
| 读秒版组件 | Gradle | `com.friday.motonav.countdown` 中间 APK |
| 读秒版最终包 | Windows + apktool + Zig + provider.apk | `com.autonavi.amapauto` |
| iOS | Xcode | 不参与当前 Android 流程 |

## 6. 架构优点与风险

**优点**

- 固件通过 `pin_config.h` 做板级解耦，1.75C 不需要改上游；
- App 板级无关，一套 BLE 协议可以驱动 1.75/1.75C 和 StopWatch；
- `ports/175c` 把移植改动收敛在一个目录，升级上游时容易对比；
- 标准版、读秒版、iOS 分开维护，互不干扰。

**风险**

- App 和固件不对称：App 可能有更多“StopWatch 专版”假设，像天气一样误伤 1.75C；
- StopWatch 协议分支在 1.75C 上休眠，目的地抽屉、主题切换等可能无反应；
- 包名修改导致 App 数据割裂，高德/和风 Key 需要重填；
- debug/release 两套签名，安装覆盖和高德 SHA1 绑定要严格区分；
- 读秒版最终包固定为 `com.autonavi.amapauto`，不能改成 `com.friday.motonav`；
- 1.75C 只使用前 16 MB 分区，后 16 MB 闲置。

## 7. 建议

1. 建立板型功能矩阵：明确 175/1.75C/StopWatch 各自支持哪些 App 功能；
2. 审计 App 里的 StopWatch 分支，标注“仅 StopWatch”，在 1.75C 上隐藏或降级；
3. 把 App 修改也做成补丁层，保持上游快照可对比；
4. 固定并备份签名 keystore，记录包名 + SHA1；
5. 标准版和读秒版分开维护，不要混用包名、Key 和安装方式。
