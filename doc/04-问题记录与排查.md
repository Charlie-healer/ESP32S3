# 问题记录与排查

记录 2026-11-08 调试 1.75C 过程中遇到的主要问题和结论。

## 1. 烧录后启动循环：QIO 覆盖了镜像头

**现象**

烧录完整镜像后，串口反复输出：

```
rst:0x7 (TG0WDT_SYS_RST)
boot:0xb (SPI_FAST_FLASH_BOOT)
mode:QIO, clock div:1
ets_loader.c 79
```

设备约每秒重启一次，应用起不来。

**原因**

镜像头本身是 **DIO / 80 MHz / 32 MB**，但烧录命令额外加了：

```text
--flash_mode qio
```

ROM 按 QIO 方式读取启动镜像，导致启动失败。

**修复**

不要覆盖镜像头参数，直接：

```bash
"$ESPTOOL" --chip esp32s3 -p /dev/cu.usbmodem2101 -b 921600 \
  write_flash 0x0 dist/MotoNav_175c_v7.12.11-175c.1_panel0_full_0x0.bin
```

重新烧录后串口不再重启，BLE 广播 `MotoNav-D111`。

**经验**

烧录前先看镜像头：

```bash
"$ESPTOOL" image-info dist/*_full_0x0.bin
```

如果没有明确理由，不要手动指定 `--flash_mode` / `--flash_freq` / `--flash_size`。

## 2. 电池显示 7%：AXP2101 电量计未校准

**现象**

电池之前充满，圆屏电量只显示 7%。

**诊断**

用 `ports/175c/diag/battery_probe` 读取 AXP2101：

```
S1=0x38 S2=0x33 present=1 vbusGood=1 chgState=1 battMv=4207 pct=20..27
```

- `S1=0x38`：电池存在，VBUS 正常；
- `S2=0x33`：正在充电，CV 恒压阶段；
- `battMv=4207`：4.207 V，接近 4.2 V 满电；
- `0xA4` 电量：20–27%，明显偏低；
- `0x18=0x0A`：电量计已使能；
- `0xA2` 改为 `0x01` 后百分比仍偏低。

**结论**

电池和充电通路正常，是 AXP2101 电量计的 SOC 估算未校准/重新学习。MotoNav 读取的寄存器与 XPowersLib、微雪官方示例一致，不是移植层写错。

**处理**

- 继续充电到满；
- 之后 App 曾显示 100%，说明电量计恢复；
- 如果再次出现，做一次完整充放电循环，或在移植层改为按电压估算百分比。

**注意**

电压 4.207 V 是在 USB 充电时读到的端电压；如果怀疑电池没接好，拔掉 USB 看设备是否继续运行。

## 3. 圆屏天气一直 loading

**现象**

圆屏和手机 App 已连接，天气页一直 loading。

**原因**

当前 8.3.26 工程来自 StopWatch 分支，删除了三处天气链路：

1. `CallWatcher.onScreenTouch` 缺少 `"W" -> Weather.request()`；
2. `NavService` 的 `Weather.init(this)` 被注释；
3. “地图 Key”页缺少和风配置入口，`showWeatherConfig()` 是死代码。

同时，新包 `com.friday.motonav` 的 `shared_prefs/qweather.xml` 不存在，没有和风 Host/Key。

**修复**

- 恢复 `CallWatcher` 的 `"W" -> Weather.request()`；
- 恢复 `NavService` 的 `Weather.init(this)`；
- 在 `MainActivity.keySection` 增加“和风天气 → 配置”入口；
- 重新编译并安装 debug APK。

安装后“地图 Key”页显示：

```
和风天气    未配置：请填写 API Host 与 API Key    配置
```

**还需要**

在和风控制台申请 API Host 与 API Key，填入 App。天气只在圆屏滑到天气页时查询，10 分钟缓存。

**排查**

```bash
adb logcat -s MotoNavWeather
```

App 的“查看天气详情与数据来源”也会显示具体错误。

## 4. 修改包名后数据丢失

**现象**

标准版从 `com.example.motonav` 改成 `com.friday.motonav` 后，原来的高德 Key、和风配置、历史记录都不见了。

**原因**

Android 的 App 数据按包名隔离。新包是全新的数据目录，不会继承旧包数据。

**处理**

- 高德 Key 重新填入（本次已重新填写，具体值不写入文档）；
- 和风 Host/Key 重新填；
- 以后改包名前先导出或记录配置。

## 5. `adb install` 返回 -99 / 空错误

**现象**

安装新包时：

```
adb: failed to install ...:
Failure [-99]
```

**原因**

手机停在指纹锁屏界面，系统的应用安装确认界面被锁屏挡住。

**处理**

- 解锁手机并保持亮屏；
- 重新执行 `adb install -r ...`；
- 如果仍然失败，用 `adb install --no-streaming -r ...`。

本次解锁后安装成功，`com.friday.motonav` 已安装并运行。

## 6. 读秒版最终包不是 `com.friday.motonav`

**现象**

用户期望读秒版最终包也叫 `com.friday.motonav`，实际是 `com.autonavi.amapauto`。

**原因**

读秒版不是独立 App，而是高德车机版的修改包：

```
android/countdown 内部组件
  → 合并进高德车机版 provider.apk
  → 最终包名 com.autonavi.amapauto
```

最终包名是宿主 App 的身份。改成 `com.friday.motonav` 会破坏高德 SDK、JNI、资源包 ID、签名权限和读秒数据源。

**处理**

- 读秒版最终包保持 `com.autonavi.amapauto`；
- 内部组件包改为 `com.friday.motonav.countdown`；
- 高德 Key 按最终包名申请；
- 如果一定要独立读秒 App，需要重写/剥离高德车机版依赖，工作量大且可能失去读秒数据。

## 7. debug / release 签名不能互相覆盖

**现象**

安装 release APK 时提示签名不一致，无法覆盖 debug APK。

**原因**

debug 和 release 使用不同的签名证书：

- debug SHA1：`86:DD:40:08:E1:EC:2A:AC:C3:12:D1:F9:99:66:96:B7:D9:46:DD:D5`
- release SHA1：`C8:A2:BB:6B:0A:5B:6B:C0:F5:B7:A6:00:4C:FE:A4:41:96:ED:F1:C1`

**处理**

- 先卸载旧包，再安装另一个签名的 APK；
- 或使用相同 keystore 重新签名；
- 高德 Key 必须与当前安装包的签名 SHA1 匹配。

## 8. 高德 Key 与 SHA1 不匹配

**现象**

地图/定位失败，天气里提示“高德定位失败”，或高德 SDK 报 `INVALID_USER_KEY`、`USERKEY_PLAT_NOMATCH`、`INVALID_USER_SCODE`。

**原因**

Key 绑定的包名 + SHA1 与实际安装包不一致，常见于：

- 改了包名；
- 换了 debug keystore；
- 用 release APK 配了 debug Key，或反过来。

**处理**

- 标准版：包名 `com.friday.motonav`，按当前 APK 的 SHA1 申请；
- 读秒版：包名 `com.autonavi.amapauto`，按最终 APK 的 SHA1 申请；
- 用 `apksigner verify --print-certs <apk>` 核对实际签名，不要凭记忆。

## 9. StopWatch 分支在 1.75C 上休眠

**现象**

App 里可能有 StopWatch 的目的地抽屉、主题切换等入口，但在 1.75C 上点击无反应。

**原因**

这些功能对应 StopWatch 固件的协议：

- `DEST_Q` / `DEST_GO` / `SET_THEME` / `#DEST`；
- 1.75 固件不发送也不处理这些命令。

**处理**

- 在 1.75C 上视为不可用；
- 如需支持，要在 1.75 固件里增加对应页面和命令处理；
- 或在 App 里按连接的板型隐藏这些入口。

## 10. 1.75C 只用了前 16 MB Flash

**现象**

1.75C 有 32 MB Flash，但分区表只有 16 MB。

**原因**

Arduino Core 3.3.10 对 ESP32-S3 只提供到 16 MB 的分区方案；`app3M_fat9M_16MB` 是 16 MB 布局。

**处理**

- 当前固件不使用 ffat，16 MB 足够；
- 以后要用满 32 MB，需要自定义分区表，并确认 bootloader/flash size 配置；
- 修改分区会清空数据。

## 11. RTC 时间重启后不恢复

**现象**

手机同步过时间后，圆屏离线运行正常；一重启就回到 `--:--` / 1970 年，或者串口打印：

```text
RTC boot time=64
```

**排查**

- AXP2101 的 SensorLib 驱动没有日期/时间接口，1.75C 板上也没有 PCF85063/PCF8563；
- 1.75C 使用 ESP32-S3 内部 RTC，由 AXP2101 的 RTCLDO/VBAT2 供电；
- 只调用 `settimeofday()` 时，系统时间偏移不跨复位保留；之前看到 `RTC boot time=1794181625` 是 App 在开机后重新同步造成的假象；
- `RTC_DATA_ATTR` 放在 `.rtc.data`，普通复位时启动代码会重新初始化，不能用来存基准；
- 改用 `RTC_NOINIT_ATTR`（`.rtc_noinit`）后，基准能跨复位保留。

**修复**

- `HomeClock::receive()` 成功解析 `#TIME` 后调用 `rtcClockSave()`；
- `rtcClockSave()` 保存本地 epoch、`esp_clk_rtc_time()` 微秒基准和 magic；
- 开机时 `rtcClockInit()` 用 `elapsed = (nowUs - baseUs) / 1000000` 恢复 `baseEpoch + elapsed`；
- magic 不匹配或计数器回退时放弃恢复，等手机重新同步。

**实测**

```text
RTC boot #... magic=4D4F544F rtcUs=261163426 baseEpoch=1794182200 baseUs=238365021
RTC restore epoch=1794182222 elapsed=22s ok=1
```

关掉 App 后复位仍能恢复，说明不依赖手机开机同步。

**限制**

完全断开电池/RTCLDO 会丢失基准；下次连接手机自动恢复。

## 12. 点击 G 按钮崩溃（QMI8658 vtable 空指针）

**现象**

点击首页右下角 G 按钮，串口打印：

```text
DEST tap x=387 y=334 open=0
Guru Meditation Error: Core 1 panic'ed (InstrFetchProhibited)
PC: 0x00000000
```

回溯落在 `leanInit()` 的 `imu.begin()`。

**原因**

SensorLib 同时存在两套同名 `SensorQMI8658`：

- 旧的 `libraries/SensorLib/src/SensorQMI8658.hpp`（deprecated，header-only）；
- 新的 `libraries/SensorLib/src/sensor/imu/qmi8658/SensorQMI8658.{hpp,cpp}`。

两套类的 mangled name 和 vtable 符号相同，链接后旧代码调用到新类的 vtable 布局，`initImpl` 槽位变成空指针。

**修复**

`ports/175c/overlay/LeanMeter.h` 改用新驱动：

```cpp
#include <sensor/imu/qmi8658/SensorQMI8658.hpp>
```

并按新 API 初始化/读取：

```cpp
imu.begin(Wire, QMI8658_L_SLAVE_ADDRESS, IIC_SDA, IIC_SCL);
imu.configAccel(SensorQMI8658::AccelRange::FS_4G, 1000.0f);
imu.enableAccel();
imu.configGyro(SensorQMI8658::GyroRange::FS_512DPS, 112.1f);
imu.enableGyro();
```

**验证**

临时在启动时调用 `leanInit()`，串口输出：

```text
LEAN: QMI8658 ready
```

不再崩溃；验证后已移除启动自检。

## 13. 点 G 按钮下方误打开设置

**现象**

VICE 完整待机页上，点击右下角 G 按钮下方（约 `x=346, y=396`），左侧远处的设置面板却被打开。

**原因**

`settingsGearHit()` 里保留了早期触摸 X 镜像的兜底判断：

```cpp
int mx = x - (LCD_WIDTH - 1 - gx);  // 466 - 1 - 120 = 345
return dx * dx + dy * dy <= 30 * 30 ||
       mx * mx + my * my <= 30 * 30;
```

镜像齿轮点正好是 `(345, 396)`，位于 G 按钮 `(346, 350)` 正下方约 46px，命中半径 30px；触摸映射修正后这个兜底不再需要，反而造成误触。

**修复**

删除镜像分支，只保留真实齿轮位置 `(120, 396)`：

```cpp
bool settingsGearHit(int x, int y) {
  const int gx = 120, gy = 396;
  int dx = x - gx, dy = y - gy;
  return dx * dx + dy * dy <= 30 * 30;
}
```

**验证**

- `settingsGearHit(346, 396)` 现在返回 false；
- G 按钮本身仍由 `leanButtonHit(346, 350)` 命中；
- 点击 G 下方不会再打开设置。

## 14. 快速排查顺序

1. **串口是否重启循环**：`rst:0x7` / `ets_loader.c 79` → 检查 flash mode；
2. **BLE 是否广播**：搜 `MotoNav-D111`；
3. **App 是否已连接并验证**：看“圆屏设置”页；
4. **电量**：`adb logcat` / 探针 / App 状态卡；
5. **天气**：`adb logcat -s MotoNavWeather`，检查和风 Host/Key；
6. **地图**：检查高德 Key 的包名 + SHA1；
7. **安装失败**：解锁手机、检查签名是否一致。
